## 课堂提问

1. **两个 Topic 平均都是 200 Hz，为什么对控制的影响可能天差地别？**
   一个每 5 ms 一条；另一个一口气来 20 条再停 100 ms。平均相同，最坏间隔差 20 倍。控制器（和 13 节的超时）要按最坏间隔设计。
2. **机器人和电脑的时钟没对过表，为什么还能分析延迟？**
   `到达时刻 − tick` = 真实延迟 + 两个时钟的固定差。差是常数，所以这个量的**变化**就是延迟的变化；若两钟快慢不同，会叠加一条直线（漂移），拟合扣掉即可。
3. **`use_sim_time` 回放时，这种延迟分析还成立吗？**
   到达时刻要用墙上时钟（`time.monotonic()`），不能用节点的仿真时钟；本节的 `RateMeter` 用的正是前者。

## 常见误解

- **"`ros2 topic hz` 显示的就是发布频率。"** 它是**你这一端收到**的频率，受网络、QoS、你自己电脑负载的影响。
- **"延迟 = 1 / 频率。"** 毫无关系。500 Hz 的 Topic 也可以每条都晚 50 ms。
- **"加负载后平均频率没掉，所以没影响。"** 先坏的是尾巴（99% 分位、最坏间隔）。多核机器上可能看不出，这时让学生把负载进程开到与核数相同再试。
- **漂移几千 ppm** 是合成数据的产物（生成程序达不到标称频率，其"机器人时钟"走得慢），真实晶振通常几十 ppm。借机强调：测量方法对，数字要在真机上重测。
- **本机回环的延迟数字**主要反映 Python 和调度开销，几十 KB 内看不出规律很正常；不要让学生从中得出"大消息更快"的结论。

## 课后作业与参考解

1. **滑动窗口**：`stamps` 用 `collections.deque`，`report(window_s)` 里筛 `t > now - window_s` 再调 `rate_stats`；用 `create_timer(1.0, ...)` 每秒打印。
2. **RPC 往返时间**：
   ```python
   bag = read_bag(DATA / "bags/go2_demo", ["/api/sport/request", "/api/sport/response"])
   sent = {r.header.identity.id: t for t, r in bag["/api/sport/request"]}
   for t, r in bag["/api/sport/response"]:
       print(r.header.identity.api_id, f"{(t - sent[r.header.identity.id]) * 1e3:.1f} ms")
   ```
   合成数据里是十几到几十毫秒（本机回环 + Python 服务端）。
3. **真机实测**：结果填入 `docs/real_robot_checklist.md` 的 B 组。预期：网线下 `/lowstate` 接近标称且尾巴短；Wi-Fi 下平均可能接近但最坏间隔明显变大。
